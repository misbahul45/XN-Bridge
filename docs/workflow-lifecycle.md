# Workflow lifecycle and operations

The generic engine supports CREATED, PLANNED, RUNNING, PAUSED, BLOCKED, AWAITING_APPROVAL, RECONCILIATION_REQUIRED, COMPLETED, FAILED and CANCELLED. Creation installs a versioned domain stage plan and normally returns PLANNED. Starting/checkpointing work moves it to RUNNING. Stage order is enforced; completion requires required stages and no unresolved execution. Terminal workflows cannot be resumed into new work through state transitions. Domain actions are validated separately; hosts remain responsible for following the planned stage sequence.

SQLite migrations run under `BEGIN IMMEDIATE`, with foreign keys, unique workflow/entity/idempotency constraints, WAL, an 8-second busy timeout and explicit transaction boundaries. Execution starts and approval consumption are atomic. A partial unique index prevents concurrent active/successful duplicate external attempts. Caller-provided dedupe keys cannot replace the canonical guard. Idempotency-key reuse with different execution parameters is rejected.

Checkpoints store stage/state/data plus event history. Large content goes into hash-addressed artifacts. On restart, `workflow_resume` returns the last checkpoint and next action without replaying unrelated completed work. Stale STARTED reads become interrupted failures; stale external attempts become OUTCOME_UNKNOWN and force reconciliation. Failed external actions can be retried only after evidence-supported reconciliation and a new approval/key.

Evidence records store source reference, captured-content digest, retrieval time, origin, verification/uncertainty, workflow and artifact link. Verification is provenance qualification, not automatic semantic proof. Model summaries cannot become VERIFIED; missing source/content, staleness, injection flags or wrong-workflow evidence prevent relevant verified transitions. CV extraction evidence must match the exact text digest.

`xnbridge backup --full --out <new.zip>` writes a consistent SQLite snapshot, all referenced artifact blobs, configuration and any encrypted approval key/public key. Archives have digests, conservative file/byte bounds, private permissions and non-overwriting publication. Symlinks and missing/corrupt referenced artifacts are rejected. `verify-backup <zip>` checks the archive without extraction. `restore <zip> --into <new-home>` validates paths, entry types/counts, digests, schema/integrity/foreign keys and artifact references before publishing a separate home. Existing destinations are refused. Pending/granted approvals are revoked, STARTED external attempts become OUTCOME_UNKNOWN, and affected workflows require reconciliation. Restoration never replays a tool.

The database-only `backup`/`restore <snapshot>` path remains supported, validates before touching the live home, revokes old approvals, rejects WAL/live/unrelated inputs, and preserves preceding files. Stop host sessions for this in-place legacy operation. Gmail credentials/tokens and host config are deliberately outside coordination backups. Full archive roundtrip and separate real-state clone restoration passed; concurrent writers were tested with four processes. WAL is not a substitute for transaction rules.

Bounds include per-step retry recommendations, total tool calls, provider switches, stage count, deadline, browser operations, payload/entity sizes and cooperative resource checks. These constrain recorded/bridge-owned actions, not direct host bypass. Context budgets and OS CPU throttling are not enforced by the bridge.

PAUSED, BLOCKED and terminal workflows reject mutating domain actions unless an action explicitly supports the pending/safe tracking case. Research source ingestion/verification and ATS-fetch-with-persistence are LOCAL_WRITE, not READ. Verification uses same-workflow evidence; research finalization rechecks freshness. Career ATS verification also rechecks a captured employer-to-board link, including during reverify, so stale identity evidence cannot keep an unrelated board verified.
