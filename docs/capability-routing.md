# Capability routing

Default logical mappings live in `src/xnbridge/defaults/capabilities.toml`; local overrides live in `data/config/capabilities.toml`. Capability IDs are not tool names. Every selected external provider must match an actual discovered server/tool and an accepted contract. Providers include schema digest, risk/cost labels, health, protocol/version and last-seen metadata. Unknown costs remain unverified configuration labels.

Call `capability_resolve("web.search")` for a selected provider, compatible fallbacks, exclusions and degraded behavior. A few bridge-native capabilities, including workflow persistence and evidence storage, need no sibling connection. Offline mode suppresses internet-dependent providers and the ATS adapter while preserving local workflow operations.

Discovery reads the selected host, initializes one configured provider at a time, paginates tools/list with a deadline/page bound, and stores full schemas locally. Repeated cursors, incomplete pagination, authentication failures and process errors cannot become healthy partial catalogs. Legacy negotiation is retried for incompatible stdio providers; HTTP is not guessed to be authentication failure without evidence. No business tools are called during discovery. Protected provider startup directories are overridden to bridge scratch locations.

Input/output schema or annotation changes, description changes, protocol/server-version changes, host permission-filter changes, and expiry invalidate selection. Changed contracts remain quarantined across rescans until accepted. Per-provider last-seen timestamps prevent a partial rescan of another server from making old schemas fresh. Codex enabled/disabled tool filters are honored. A changed host fingerprint excludes old providers until rediscovery. Credentials and environment values are not retained in the fingerprint.

On a safe read failure, record the attempt and use its bounded recovery recommendation. Resolve again excluding the failed provider. Repeated health failures create a cooldown and prefer healthy alternatives. Permission/authentication denials require user intervention; do not route around them. External timeouts require reconciliation and never automatic replay. The host validates actual sibling argument/output schemas and performs the call; the bridge is not a universal tool executor.

After expanding contract hashes to include output schemas/annotations, old catalog entries were quarantined. Five reviewed current contracts were accepted: web search/fetch, MarkItDown extraction, PDF generation, and graph search. Other contracts remain quarantined. Initialization was healthy for Xninetzy, but actual calls returned `POLICY_HELD: approval_channel_unverified`; this operational limitation is recorded in bridge health. `catalog changed` and `catalog accept --server … --tool …` provide explicit local review, independently of human submission approvals.

`discover --via-host --only <servers>` reuses native Codex discovery. `--watch-seconds` requires an explicit selection and is bounded to 300 seconds with at least one second between polls. Native startup-status notifications invalidate relevant entries; periodic inventory covers subsequent changes. The installed API does not expose negotiated MCP revision or a complete tool-list subscription, so observed revisions are preserved and forwarding is not assumed. Identical snapshots reuse their raw artifact; changing a schema, description, filters or version creates a new captured contract. A partial refresh under a changed host fingerprint marks other providers stale rather than making them fresh implicitly.

Use `catalog describe --server <server> --tool <tool>` to load one full contract. `catalog changed --limit 50 --offset 0` paginates compact changed records. Authentication and permission holds survive successful initialize/list. `catalog health --server … --status … --detail …` records a local operator observation and audit event, without granting host/account access. Do not clear a hold based on metadata alone.

The installed `career-public:search_jobs` is a `career.listings` candidate with an observed contract and an actual successful public read. `email.read` maps to two of Gmail's three reviewed read tools, but is DEGRADED while Gmail is AUTH_REQUIRED. No Gmail send or external draft tool is mapped. Exact risk rules cover reviewed operations; unknown/new tools retain EXTERNAL_WRITE risk. Source polling limits are described in [MCP integration operations](mcp-integrations.md).
