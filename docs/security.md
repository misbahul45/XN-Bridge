# Security and authorization

Operations are classified READ, LOCAL_WRITE or EXTERNAL_WRITE from explicit local policy and stage risk. Unknown providers fail closed. Browser form interactions may autosave, so potentially mutating interactions are escalated to external-write risk by stage/context. Broad read heuristics and configured cost classes are operator policy, not proof that a provider is benign.

Bridge-managed external attempts need a signed, expiring approval bound to workflow, action, exact destination/origin and payload digest. Approvals are consumed atomically once. There is no MCP grant tool or `approved: true` argument. The human CLI requires an interactive terminal and an encrypted Ed25519 key passphrase. No real approval key was created for this installation. Fixture keys and simulated human approval prove local behavior only.

Human review shows the exact text/artifact payload and all attachment handles, escapes terminal controls/bidirectional markers, and fails closed if content cannot be displayed. Review is not truncated at 6,000 characters. Manifest attachment and text blobs are digest/ownership checked at prepare, grant and consumption; changing their bytes after a signature invalidates the approval. Restoring state revokes pending/granted approvals and marks interrupted external execution uncertain, preventing archive rollback from reactivating old grants.

**The bridge is not an enforcement boundary around the host.** The installed Codex API can directly call MCP tools without creating bridge execution records; the harmless host test demonstrates this bookkeeping bypass. It does not attempt an unauthorized external write. A host with shell access can also alter local policy/state; the signing files and TTY checks are not isolation from the same local account. Real applications must be submitted manually unless an independent host approval boundary is verified. Manifest generation alone never authorizes submission.

External timeouts and missing confirmation become OUTCOME_UNKNOWN, with no automatic resubmission. Reconciliation requires fresh usable evidence from the same workflow. Changed payloads, replayed signatures, wrong targets, custom dedupe-key bypasses and changed idempotent requests are rejected in security tests. Deduplication is scoped to a workflow/action/target, so cross-campaign resubmission still needs operator review.

Documents, pages and tool output are untrusted. Injection-pattern detection flags suspicious content and blocks its promotion to usable verified evidence; it is a heuristic, not a complete semantic injection detector. The router has a closed output vocabulary and cannot change policy or grant approval. Host-generated facts or `user_confirmed` markers are assertions whose authenticity must come from the host/user conversation.

Data directories use mode 0700; artifacts, encrypted keys and new database backups use private file permissions. State is plaintext local SQLite/files unless the user's filesystem supplies encryption. No credentials are intentionally stored in evidence or reports; avoid passing credentials in raw tool content, since raw artifacts deliberately preserve captured data locally. Sensitive read paths and path traversal are rejected. Artifact reads verify content digests.

The ATS adapter accepts fixed public HTTPS hosts and validated slugs, bounds response bytes/time, rejects redirects, and checks resolved addresses. General URL validation rejects private/reserved targets and credentials. DNS checking followed by a separate client resolution is not complete DNS-rebinding protection; host/browser tools have independent network policy. Discovery of remote HTTP registrations is opt-in and never takes over host credentials.

Known ATS hostnames do not establish employer ownership. An external ATS apply target needs an exact board link captured in fresh usable evidence from the verified employer domain. A lookalike suffix hostname or unrelated board stays LISTED_UNCERTAIN. The final apply URL is checked, rather than allowing a benign display URL to validate a different destination. Evidence links are parsed once per company per bounded batch and revalidated on each later action; no cross-request freshness cache is introduced.

New provider boundary: public-job tools use fixed public APIs; their output can be partial, truncated or misleading and remains untrusted. Gmail runs readonly/core with exactly three host-allowed tools; actual Codex invocation of its send tool was rejected. The launcher adds strict loopback callback Host/Origin checks, disables single-user missing-state fallback and disables telemetry export. Account OAuth is still unconfigured. The optional callback exists only on demand for browser OAuth; no MCP HTTP transport was enabled. Tests exercise missing-code/host/origin rejection without tokens. These controls do not prevent the owner account's shell from modifying the launcher or host settings. See [integration limits](mcp-integrations.md).

Observed external dependency policy: `security_scope`, `web_search` and `web_fetch` on the connected Xninetzy service returned `POLICY_HELD: approval_channel_unverified`. The existing [Playwright skill](../../../.codex/skills/playwright/SKILL.md) delegates browser use to its [MCP workflow reference](/home/misbahul45/.codex/skills/playwright/references/mcp-workflows.md), which says: “Refuse to drive a browser against any host not in scope.” Browser execution was held at that prerequisite. No bypass, CAPTCHA solving, employer communication, upload of private documents, or real submission occurred.
